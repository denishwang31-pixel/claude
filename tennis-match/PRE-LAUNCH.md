## A. 이게 안 되면 출시 자체가 막힌다

- [ ] **개인정보처리방침 · 이용약관** — 앱에도, 웹에도 없다.
      구글 플레이는 개인정보처리방침 URL 없이는 등록 자체가 안 된다.
      이 앱은 전화번호·이름·성별·푸시토큰을 모으므로 필수 기재 대상이다.
      앱 안에도 링크가 있어야 한다(더보기 하단이 자연스럽다).

- [ ] **계정 삭제 수단** — 구글·애플 모두 "가입할 수 있으면 앱 안에서
      지울 수도 있어야 한다"를 심사 항목으로 강제한다. 지금은 클럽
      탈퇴만 있고 계정 자체를 지우는 길이 없다.

- [ ] **Firebase 키가 자리표시자다** — `firebaseConfig.js` 가
      `YOUR_API_KEY` 인 상태로 저장소에 있다. 실제 키를 넣되
      저장소에 그대로 커밋하지 말고 EAS Secrets / `.env` 로 뺀다.

- [ ] **전화번호 인증 방식 결정 (R-1)** — 지금은 Firebase JS SDK 골격이고
      `expo-firebase-recaptcha` 는 이미 deprecated 다. 실사용 인증을
      본격적으로 열려면 `@react-native-firebase/auth` + dev build 로
      갈아타야 한다. 사람이 늘기 전에 정해야 데이터 이관이 없다.

- [ ] **⏰ Cloud Functions 런타임 Node 20 → 22 (기한: 2026-10-30)**
      Node 20 은 2026-04-30 에 지원 종료됐고 **2026-10-30 에 완전히 내려간다.**
      그 뒤로는 배포 자체가 거부되므로, 급한 수정이 생겨도 못 올린다.
      고칠 곳은 두 군데뿐이다 — `functions/package.json` 의 `engines.node`,
      `firebase.json` 의 `functions.runtime`. 다만 런타임을 바꾸면 배포가
      한 번 흔들릴 수 있으므로 **다른 작업이 없는 날에** 올리고 함수 15개가
      모두 살아 있는지 확인한다. 출시 일정이 10월 이후면 이건 선택이 아니다.

- [ ] **⚠️ `extra.eas.projectId` 가 app.json 에 없다 — 알림이 전부 죽는다**
      푸시 토큰을 받으려면 이 값이 있어야 한다. 없으면
      `getExpoPushTokenAsync()` 가 예외를 던지고, 예전 코드는 그것을 조용히
      삼켰다. 그러면 **서버는 멀쩡히 보내는데 받을 토큰이 저장되지 않아
      아무도 못 받는다** — 회비 독촉도, 참석 투표 요청도, 교류전 초대도.

      `eas init` 또는 `eas update:configure` 를 실행하면 채워진다.
      2026-08-18 에 실패 사유를 콘솔에 남기도록 고쳤으므로, 다음 빌드에서
      `[알림]` 경고가 뜨는지 확인하고 **회원 문서에 pushToken 이 실제로
      저장되는지** 한 번은 눈으로 봐야 한다.

- [ ] **`expo-updates` — 설정은 넣었고 빌드 1회가 남았다** (2026-08-18 착수)
      패키지·`runtimeVersion`(appVersion 정책)·채널(development/preview/
      production)까지 넣었다. 남은 것은 `eas update:configure` 한 번과
      **빌드 1회**다. 네이티브 모듈이라 OTA 로는 스스로를 넣을 수 없다.

      그 빌드가 끝나면 JS 변경은 `eas update --branch preview` 로 몇 초 만에
      나간다. 최근 작업(참석 투표·교류전·대진표 표시)은 전부 자바스크립트였고,
      2026-08 에 EAS 안드로이드 무료 한도(월 15회)가 떨어져 13일 밀린 것도
      이것만 있었으면 겪지 않았다.

      **주의**: `runtimeVersion` 이 `version`(0.1.0)을 따른다. 네이티브가
      바뀌면 `version` 을 올려야 옛 빌드가 못 받는 JS 를 받지 않는다.
      네이티브를 그대로 두고 `version` 만 올리면 기존 사용자가 업데이트를
      못 받으므로, 이 값은 함부로 건드리지 않는다.

- [ ] **앱 아이콘 · 스플래시 · 스토어 스크린샷 · 소개문구** — 미착수.

- [ ] **버전 체계** — `app.json` 이 `0.1.0` / `versionCode: 1` 그대로다.
      출시 전에 1.0.0 으로 올리고, 이후 빌드마다 versionCode 를 올리는
      규칙을 정해 둔다(안 올리면 업로드가 거부된다).

## B. 지금은 편해서 켜 둔 것 — 남 앞에 내보내기 전에 꺼야 한다

- [ ] **운영진 ↔ 회원 보기 모드 전환** — 내가 두 화면을 다 확인하려고
      넣은 테스트 장치다. 실제 회원이 보면 "내가 운영진인가?" 하고
      헷갈린다. 개발자 계정에만 보이게 하거나 빼는 것이 맞다.

- [ ] **온보딩 다시 열기(resetOnboarding)** — 홈·더보기에서 온보딩을
      다시 띄울 수 있다. 편의 기능이지만 일반 사용자에게는 나갈 길처럼
      보인다. "다른 클럽 찾기"만 남기고 정리한다.

- [ ] **데모 시드 데이터** — 클럽을 만들 때 `seedClub(clubId, withDemo)`
      로 가짜 회원·모임이 들어갈 수 있다. 실서비스 기본값은 반드시
      `withDemo = false` 여야 한다. 남의 클럽에 모르는 이름이 들어가 있는
      것만큼 신뢰를 빨리 깎는 것이 없다.

- [ ] **오프라인 등록 회원(`local:` 아이디)** — 총무가 손으로 추가한
      회원은 로그인할 수 없는 유령 계정이다. 지금은 대진·회비 계산에는
      들어가는데 본인은 앱을 못 쓴다. 나중에 그 사람이 실제로 가입했을 때
      **기존 기록과 합치는 방법**이 없다. 합치기 기능이 필요하다.

- [ ] **카카오 지도 키 없음** — `keys.js` 가 빈 문자열이라 코트 지도가
      간이 모드로만 뜬다. 기능 저하일 뿐 죽지는 않지만, 코트 검색이
      이 앱의 유입 경로라면 출시 전에 넣는 것이 낫다.

- [ ] **앱 관리자 등록이 수동** — `appAdmins/{uid}` 문서를 Firebase 콘솔에서
      직접 만들어야 용품 탭을 관리할 수 있다. 나 혼자면 괜찮지만
      인수인계가 불가능한 구조다.

## C. 사람이 늘면 조용히 터지는 것

- [ ] **⚠️ 회비 독촉 로직이 두 벌인데 대조 장치가 없다**
      `src/lib/dunning.js` 와 `functions/index.js` 의 `DUN_STAGES`·문구가
      각자 존재한다. `firebase deploy` 는 `functions/` 만 올리므로 서버가
      앱 코드를 읽을 수 없어 생긴 구조인데, **한쪽만 고치면 앱 화면과
      실제 발송이 어긋난다.** 돈 문제라 어긋나도 한참 뒤에 발견된다.
      → 참석 투표에서 쓴 방식(`scripts/test-rsvp.mjs`)을 그대로 적용해
        두 구현을 같은 입력으로 대조하면 된다. **이 목록에서 가장 먼저
        갚아야 할 빚이다.**

- [ ] **모임 구독에 기간 제한이 없다** — `subMeetings` 가 클럽의 모든
      모임을 통째로 구독한다. 주 2회 × 2년이면 200건이 넘고, 앱을 켤 때마다
      전부 읽는다. 읽기 비용과 체감 속도 양쪽에 걸린다.
      최근 N개월로 자르고 과거는 따로 조회한다. (기존 FIX-09)

- [ ] **채팅을 300개 받아 앱에서 거른다** — 채널별 서버 필터를 쓰면
      복합 색인이 필요해서 지금은 최근 300개를 받아 화면에서 나눈다.
      코트장이 많아지고 대화가 늘면 오래된 채널 글이 안 보이기 시작한다.
      그때 색인을 만들고 서버 필터로 바꾼다.

- [ ] **푸시 발송에 실패 처리가 없다** — Expo Push 응답을 읽지 않아서,
      만료된 토큰(`DeviceNotRegistered`)이 계속 쌓인다. 지운 앱에도 계속
      쏘는 셈이라 발송량만 늘고 아무도 못 받는다. 응답을 보고 죽은 토큰을
      지우는 처리가 필요하다.

- [ ] **교류전 초대에 만료가 없다** — 상대가 수락도 거절도 안 하면
      "수락 대기"로 영원히 남는다. 경기 날짜가 지난 초대는 자동으로
      닫아야 목록이 쓰레기통이 되지 않는다.

- [ ] **교류전 명단에 상대 클럽 회원 이름이 남는다** — 우리 클럽
      문서가 아닌 곳(루트 `clubMatches`)에 상대 회원의 이름·성별이
      복사된다. 상대 클럽이 앱을 탈퇴해도 이 기록은 남으므로,
      개인정보처리방침에 보관 기간과 삭제 방법을 적어야 한다.
      (A의 개인정보처리방침 항목과 같이 처리한다)

- [ ] **코트 데이터가 손으로 만든 눈금이다** — `courtsSeoul.generated.js`
      는 한 시점에 긁어 온 값이다. 예약 링크가 바뀌면 조용히 죽는다.
      정기적으로 다시 받는 절차(또는 사용자 신고 버튼)가 필요하다.

## D. 외부 계약·비용이 걸린 것 (돈과 시간이 필요하다)

- [ ] **카카오 알림톡** — 앱을 안 까는 회원(특히 40~60대)이 이 앱의 가장 큰
      구멍이다. 정답이지만 카카오 비즈메시지 채널 개설 + 발신프로필 심사가
      먼저다. 건당 8~9원, 회원 30명 × 월 4건이면 월 1,080원 수준.

- [ ] **고정형 가상계좌** — 입금자명 문제가 원천 소멸한다. 단 PG 계약이
      필요하고, 앱이 돈을 직접 보관하면 전자금융거래법(선불전자지급수단)에
      걸리므로 **PG사 명의 계좌 + 정산 대행** 형태로만 가능하다.
      통신판매중개업 신고도 따라온다.

- [ ] **영수증 OCR** — 지출 등록 자동화. 외부 OCR 연동 필요.

- [ ] **스토어 비용** — Google Play $25(1회), Apple Developer $99(연).

- [ ] **Blaze 요금제** — Cloud Functions 를 쓰는 순간 필수다. 무료 쿼터
      안에서 돌지만 카드 등록은 되어 있어야 한다.

## 갱신 규칙

기능을 추가하거나 요구사항을 반영할 때마다:

1. 그 기능이 **지금은 괜찮지만 남이 쓰면 곤란한 부분**을 A~D 중 맞는 곳에 적는다.
2. 빚을 갚았으면 E로 옮기고 **날짜와 검증 방법**을 같이 남긴다.
3. 맨 위 "마지막 갱신" 날짜를 고친다.

적을 것이 없다고 판단했으면 그것도 괜찮다. 다만 "없다"고 확인한 것과
"안 봤다"는 다르므로, 애매하면 적어 두는 쪽을 택한다.
