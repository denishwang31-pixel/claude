# 정식 출시 전 정리 목록

> **이 문서의 용도**
> 지금 우리 클럽에서 쓰는 데는 문제가 없지만, **낯선 사람이 스토어에서
> 받아 쓰기 시작하면 곤란해지는 것들**을 모아 둔다.
>
> "나중에 하자"는 말은 반드시 잊힌다. 그래서 기능을 하나 추가할 때마다
> 그 기능이 남긴 빚도 여기에 같이 적는다.
>
> - 상태는 `[ ]` 미처리 / `[x]` 처리됨 으로만 표시한다.
> - 처리된 항목은 지우지 않는다. 지우면 "이거 했었나?"를 다시 조사하게 된다.
> - 마지막 갱신: 2026-08-19 (코치 광고비 방향 정정까지)

## A. 이게 안 되면 출시 자체가 막힌다

- [ ] **개인정보처리방침 · 이용약관** — 앱에도, 웹에도 없다.
      구글 플레이는 개인정보처리방침 URL 없이는 등록 자체가 안 된다.
      이 앱은 전화번호·이름·성별·푸시토큰을 모으므로 필수 기재 대상이다.
      앱 안에도 링크가 있어야 한다(더보기 하단이 자연스럽다).

- [ ] **계정 삭제 수단** — 구글·애플 모두 "가입할 수 있으면 앱 안에서
      지울 수도 있어야 한다"를 심사 항목으로 강제한다. 지금은 클럽
      탈퇴만 있고 계정 자체를 지우는 길이 없다.

- [ ] **Firebase 키가 자리표시자다** — `firebaseConfig.js` 가
      `YOUR_API_KEY` 인 상태로 저장소에 있다. 실제 키를 넣되
      저장소에 그대로 커밋하지 말고 EAS Secrets / `.env` 로 뺀다.

- [ ] **전화번호 인증 방식 결정 (R-1)** — 지금은 Firebase JS SDK 골격이고
      `expo-firebase-recaptcha` 는 이미 deprecated 다. 실사용 인증을
      본격적으로 열려면 `@react-native-firebase/auth` + dev build 로
      갈아타야 한다. 사람이 늘기 전에 정해야 데이터 이관이 없다.

- [ ] **⚠️ `extra.eas.projectId` 가 app.json 에 없다 — 알림이 전부 죽는다**
      푸시 토큰을 받으려면 이 값이 있어야 한다. 없으면
      `getExpoPushTokenAsync()` 가 예외를 던지고, 예전 코드는 그것을 조용히
      삼켰다. 그러면 **서버는 멀쩡히 보내는데 받을 토큰이 저장되지 않아
      아무도 못 받는다** — 회비 독촉도, 참석 투표 요청도, 교류전 초대도.

      `eas init` 또는 `eas update:configure` 를 실행하면 채워진다.
      2026-08-18 에 실패 사유를 콘솔에 남기도록 고쳤으므로, 다음 빌드에서
      `[알림]` 경고가 뜨는지 확인하고 **회원 문서에 pushToken 이 실제로
      저장되는지** 한 번은 눈으로 봐야 한다.

- [ ] **`expo-updates` — 설정은 넣었고 빌드 1회가 남았다** (2026-08-18 착수)
      패키지·`runtimeVersion`(appVersion 정책)·채널(development/preview/
      production)까지 넣었다. 남은 것은 `eas update:configure` 한 번과
      **빌드 1회**다. 네이티브 모듈이라 OTA 로는 스스로를 넣을 수 없다.

      그 빌드가 끝나면 JS 변경은 `eas update --branch preview` 로 몇 초 만에
      나간다. 최근 작업(참석 투표·교류전·대진표 표시)은 전부 자바스크립트였고,
      2026-08 에 EAS 안드로이드 무료 한도(월 15회)가 떨어져 13일 밀린 것도
      이것만 있었으면 겪지 않았다.

      **주의**: `runtimeVersion` 이 `version`(0.1.0)을 따른다. 네이티브가
      바뀌면 `version` 을 올려야 옛 빌드가 못 받는 JS 를 받지 않는다.
      네이티브를 그대로 두고 `version` 만 올리면 기존 사용자가 업데이트를
      못 받으므로, 이 값은 함부로 건드리지 않는다.

- [ ] **앱 아이콘 · 스플래시 · 스토어 스크린샷 · 소개문구** — 미착수.

- [ ] **버전 체계** — `app.json` 이 `0.1.0` / `versionCode: 1` 그대로다.
      출시 전에 1.0.0 으로 올리고, 이후 빌드마다 versionCode 를 올리는
      규칙을 정해 둔다(안 올리면 업로드가 거부된다).

## B. 지금은 편해서 켜 둔 것 — 남 앞에 내보내기 전에 꺼야 한다

- [ ] **운영진 ↔ 회원 보기 모드 전환** — 내가 두 화면을 다 확인하려고
      넣은 테스트 장치다. 실제 회원이 보면 "내가 운영진인가?" 하고
      헷갈린다. 개발자 계정에만 보이게 하거나 빼는 것이 맞다.

- [ ] **온보딩 다시 열기(resetOnboarding)** — 홈·더보기에서 온보딩을
      다시 띄울 수 있다. 편의 기능이지만 일반 사용자에게는 나갈 길처럼
      보인다. "다른 클럽 찾기"만 남기고 정리한다.

- [ ] **데모 시드 데이터** — 클럽을 만들 때 `seedClub(clubId, withDemo)`
      로 가짜 회원·모임이 들어갈 수 있다. 실서비스 기본값은 반드시
      `withDemo = false` 여야 한다. 남의 클럽에 모르는 이름이 들어가 있는
      것만큼 신뢰를 빨리 깎는 것이 없다.

- [ ] **오프라인 등록 회원(`local:` 아이디)** — 총무가 손으로 추가한
      회원은 로그인할 수 없는 유령 계정이다. 지금은 대진·회비 계산에는
      들어가는데 본인은 앱을 못 쓴다. 나중에 그 사람이 실제로 가입했을 때
      **기존 기록과 합치는 방법**이 없다. 합치기 기능이 필요하다.

- [ ] **카카오 지도 키 없음** — `keys.js` 가 빈 문자열이라 코트 지도가
      간이 모드로만 뜬다. 기능 저하일 뿐 죽지는 않지만, 코트 검색이
      이 앱의 유입 경로라면 출시 전에 넣는 것이 낫다.

- [ ] **앱 관리자 등록이 수동** — `appAdmins/{uid}` 문서를 Firebase 콘솔에서
      직접 만들어야 용품 탭을 관리할 수 있다. 나 혼자면 괜찮지만
      인수인계가 불가능한 구조다.

## C. 사람이 늘면 조용히 터지는 것

- [ ] **모임 구독에 기간 제한이 없다** — `subMeetings` 가 클럽의 모든
      모임을 통째로 구독한다. 주 2회 × 2년이면 200건이 넘고, 앱을 켤 때마다
      전부 읽는다. 읽기 비용과 체감 속도 양쪽에 걸린다.
      최근 N개월로 자르고 과거는 따로 조회한다. (기존 FIX-09)

- [ ] **채팅을 300개 받아 앱에서 거른다** — 채널별 서버 필터를 쓰면
      복합 색인이 필요해서 지금은 최근 300개를 받아 화면에서 나눈다.
      코트장이 많아지고 대화가 늘면 오래된 채널 글이 안 보이기 시작한다.
      그때 색인을 만들고 서버 필터로 바꾼다.

- [ ] **교류전 초대에 만료가 없다** — 상대가 수락도 거절도 안 하면
      "수락 대기"로 영원히 남는다. 경기 날짜가 지난 초대는 자동으로
      닫아야 목록이 쓰레기통이 되지 않는다.

- [ ] **교류전 명단에 상대 클럽 회원 이름이 남는다** — 우리 클럽
      문서가 아닌 곳(루트 `clubMatches`)에 상대 회원의 이름·성별이
      복사된다. 상대 클럽이 앱을 탈퇴해도 이 기록은 남으므로,
      개인정보처리방침에 보관 기간과 삭제 방법을 적어야 한다.
      (A의 개인정보처리방침 항목과 같이 처리한다)

- [ ] **코트 데이터가 손으로 만든 눈금이다** — `courtsSeoul.generated.js`
      는 한 시점에 긁어 온 값이다. 예약 링크가 바뀌면 조용히 죽는다.
      정기적으로 다시 받는 절차(또는 사용자 신고 버튼)가 필요하다.

## D. 외부 계약·비용이 걸린 것 (돈과 시간이 필요하다)

- [ ] **카카오 알림톡** — 앱을 안 까는 회원(특히 40~60대)이 이 앱의 가장 큰
      구멍이다. 정답이지만 카카오 비즈메시지 채널 개설 + 발신프로필 심사가
      먼저다. 건당 8~9원, 회원 30명 × 월 4건이면 월 1,080원 수준.

- [ ] **고정형 가상계좌** — 입금자명 문제가 원천 소멸한다. 단 PG 계약이
      필요하고, 앱이 돈을 직접 보관하면 전자금융거래법(선불전자지급수단)에
      걸리므로 **PG사 명의 계좌 + 정산 대행** 형태로만 가능하다.
      통신판매중개업 신고도 따라온다.

- [ ] **영수증 OCR** — 지출 등록 자동화. 외부 OCR 연동 필요.

- [ ] **스토어 비용** — Google Play $25(1회), Apple Developer $99(연).

- [ ] **Blaze 요금제** — Cloud Functions 를 쓰는 순간 필수다. 무료 쿼터
      안에서 돌지만 카드 등록은 되어 있어야 한다.

- [ ] **소셜 로그인 (카카오 · 구글 · 네이버)** — 앱 쪽 판단 로직은 넣었다
      (`src/lib/social.js`). 지금은 키가 없어 버튼이 **안 그려진다**.
      눌러도 안 되는 버튼을 두면 앱이 고장 난 줄 알기 때문이다.

      받아야 하는 것
        카카오  developers.kakao.com → 앱 생성 → Android 플랫폼 등록
                (패키지명 + 키 해시) → 카카오 로그인 켜기 → Redirect URI
                → REST API 키 · 네이티브 앱 키
        구글    Firebase 콘솔 → Authentication → Google 사용 설정
                → Google Cloud 에서 Android OAuth 클라이언트(SHA-1 지문)
                → 웹 클라이언트 ID · 안드로이드 클라이언트 ID
        네이버  developers.naver.com → 애플리케이션 등록 → 네이버 로그인
                사용 → Android 패키지명 → Client ID · Secret

      코드로 해야 하는 것 (키가 온 뒤)
        · `expo-auth-session` + `expo-web-browser` 추가
        · 카카오·네이버는 Firebase 가 모르는 제공자다. 받은 토큰을 검증해
          Firebase 커스텀 토큰으로 바꿔 주는 Cloud Function 이 하나 필요하다.
          구글은 Firebase 기본 제공자라 서버가 필요 없다.
        · `SOCIAL_CONFIG` 에 키를 넣는다. 코드에 직접 적지 말고 app.json 의
          extra 나 EAS 시크릿에서 읽어 넣는다.

      ⚠️ **APK 를 새로 빌드해야 한다.** 네이티브 모듈이 들어가므로
      `eas update` (OTA) 로는 안 나간다. `needsNativeRebuild()` 가 이걸
      코드에서도 알려 준다.

- [ ] **앱 안에서 카드 결제 (PG 계약)** — 회비를 "납부" 누르면 카드로 결제되고
      자동으로 납부 처리되는 것. 사업자등록증 · 정산계좌 · PG 심사가 필요하고
      건당 수수료(대략 2~3%)가 붙는다.

      **지금은 대신 이렇게 동작한다** (계약 없이 이미 됨)
        [내 회비] → 미납 달의 [납부하기] → 토스/카카오페이/네이버페이 중 선택
        → 송금 앱이 계좌·금액이 채워진 채 열린다 → 회원은 확인만 누른다.
        입금되면 총무가 [입금 대사]에서 확인해 납부로 바꾼다.
        수수료 0원이고, 클럽 규모에서는 이쪽이 오히려 낫다.

      켜는 법: [클럽 설정] → 회비 받을 계좌 에 은행·계좌번호를 넣는다.
      카카오페이·네이버페이는 총무가 자기 앱에서 만든 송금 링크를 붙여
      넣으면 그 버튼도 생긴다(개인 송금 딥링크는 공개된 방식이 없다).

      ⚠️ **실기기에서 한 번은 확인해야 한다.** 토스 송금 주소
      (`supertoss://send?...`)는 토스가 문서로 공개한 규격이 아니라 널리
      쓰이는 방식이다. 안 열리면 앱이 계좌번호를 복사해 주도록 해 두었으니
      회원이 막다른 길에 갇히지는 않는다.

- [ ] **용품 드랍십 (앱에서 직접 주문받기)** — 상품 등록 화면에 [드랍십] 방식과
      공급가·마진 계산은 넣었다(`src/lib/dropship.js`). 주문 상태 흐름과
      보안 규칙도 만들어 두었다. 하지만 **실제로 주문을 받으면 안 된다** —
      아래가 먼저다.

        · 사업자등록 (통신판매업 신고 포함)
        · 결제 수단 — 위의 PG 계약과 같은 문제다
        · 교환·반품 규정 고지 (전자상거래법)
        · 공급처와의 발주 계약 (재고·배송·반품 책임 범위)

      **초기에는 링크형만 쓰는 것이 맞다.** 판매처로 보내기만 하면 앱은
      "판매자"가 아니라서 위 의무가 생기지 않는다. 제휴에 가입하면
      링크에 코드만 붙여 수수료를 받을 수 있다(`src/lib/ads.js` 의
      `PARTNERS` 에 코드만 채우면 화면은 그대로).

- [ ] **⭐ 코치 광고 월 구독 결제 (이 앱의 수익모델)** — 나중에 만든다. 기록만.

      **돈의 방향을 다시 못박아 둔다: 코치가 앱에 낸다.**
      코치는 영상 노출로 유튜브 구독자와 레슨 문의를 얻고, 그 대가로 월
      광고비(3~5만원)를 앱에 낸다. (2026-08-19 이전 메모에는 반대로
      적혀 있었다 — 그때는 앱이 코치에게 주는 것으로 잘못 알았다)

      **지금 되는 것**: [코치 승인·광고비] 화면에서 청구서를 만들고, 입금을
      손으로 확인해 표시한다. 청구·입금·미수금 합계가 나온다. 광고가 나갔는데
      청구서를 안 만든 코치는 경고로 잡아 준다(그대로 두면 못 받는 돈이다).
      무료 체험·초기 입점 혜택은 [면제]로 둔다.

      **나중에 만들 것 — 자동 구독 결제**
        · 코치가 카드를 등록하면 매월 자동으로 결제되는 정기 구독
        · 결제 실패 / 미납이 며칠 지나면 광고(영상)를 자동으로 내릴지
          — 정책을 먼저 정해야 한다. 지금은 앱 주인이 손으로 내린다.
        · 세금계산서·현금영수증 발행 (코치는 대개 사업자다)
        · 코치가 자기 청구·결제 내역을 보는 화면 (지금은 앱 주인만 본다)

      **필요한 것**
        · 사업자등록 + PG 계약 (정기결제/빌링키 지원 상품이어야 한다.
          일반 결제만 되는 상품은 매달 코치가 직접 결제해야 해서 의미가 없다)
        · 구독 결제는 앱스토어 정책도 본다. **디지털 콘텐츠 구독이면 인앱결제를
          강제당할 수 있고 수수료가 15~30%다.** 다만 이건 "코치가 광고를
          싣는 대가"이므로 광고 상품에 가깝고, 광고비는 보통 인앱결제 대상이
          아니다. 스토어 심사 전에 확인이 필요하다 — 여기서 틀리면 앱이
          리젝된다.
        · 약관에 광고 게재 조건·환불 규정을 적어야 한다 (A의 이용약관과 함께)

      **당분간은 계좌이체가 낫다.** 코치가 몇 명일 때 PG 수수료와 심사 시간을
      들일 이유가 없다. 지금 장부만으로도 누가 안 냈는지는 정확히 보인다.

- [ ] **코치 영상 저작권·검수 기준** — 승인이 곧 지급 결정이라 기준이 필요하다.
      지금은 유튜브 링크만 받는다(직접 업로드는 저장 비용과 검수 부담이 커서
      열지 않았다). 남의 영상을 자기 것처럼 올리는 경우를 어떻게 걸러낼지,
      승인 후 영상이 삭제되면 지급을 어떻게 할지 정해 두어야 한다.

      한 번에 들어온 요구 여섯 가지 중 앱 안에서 끝나는 것을 만들었다.

      · **코치 영상 승인** — 코치가 유튜브 링크로 올리고, 앱 주인이 승인해야
        회원에게 보인다. 승인이 곧 "이번 달 지급"이므로 승인한 사람과 시각을
        남긴다. 반려는 사유 없이는 안 된다 — 코치가 무엇을 고칠지 모른 채
        같은 것을 다시 내는 왕복을 막기 위해서다.
      · **코치 검색** — 시/도 → 시·군·구. 사는 곳뿐 아니라 **가르치는 코트의

        나온다. 이걸 안 하면 출강 코치가 검색에서 통째로 사라진다.
      · **코치 프로필** — 경력·자격증·레슨 코트·레슨 시간·레슨비 안내.
        예약·결제·코치 관리는 요구대로 넣지 않았다.
      · **광고비 청구** — 그 달에 **광고가 실제로 나간**(승인된 영상이 있는)
        코치만 청구 대상이 된다. 노출이 없으면 받을 근거도 없다. 금액은
        3~5만원 범위를 벗어나면 화면이 막고, 문서 id 를 `코치_년월`로 계산해
        같은 달에 두 번 청구되는 것을 구조적으로 막았다.
        ※ 처음에는 이 돈의 방향을 **거꾸로** 만들었다(앱이 코치에게 지급).
          2026-08-19 같은 날 바로잡았다. 코치가 앱에 내는 것이 맞다.

        "시/도 + 정규화한 이름"을 키로 쓴다 — "올림픽공원 테니스장",
        "올림픽공원테니스장", "올림픽공원 코트"가 한 곳으로 모인다.

## 갱신 규칙

기능을 추가하거나 요구사항을 반영할 때마다:

1. 그 기능이 **지금은 괜찮지만 남이 쓰면 곤란한 부분**을 A~D 중 맞는 곳에 적는다.

3. 맨 위 "마지막 갱신" 날짜를 고친다.

적을 것이 없다고 판단했으면 그것도 괜찮다. 다만 "없다"고 확인한 것과
"안 봤다"는 다르므로, 애매하면 적어 두는 쪽을 택한다.
