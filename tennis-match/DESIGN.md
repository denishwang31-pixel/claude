# 테니스매치 — 디자인 · UI 안내서

외부 검토를 위해 쓴 문서다. 이 앱이 **무엇을 위한 것인지**, **기능들이 어떻게
엮여 도는지**, 그리고 **지금 UI가 어떤 규칙 위에 서 있는지**를 한자리에 모았다.

읽는 순서: 1장(목적) → 2장(사람) → 3장(화면 지도) → 4장(기능 연계)까지 읽으면
맥락이 선다. 5~8장은 디자인 시스템 자체다. **9장은 우리가 스스로 약하다고
보는 곳**이라, 검토가 가장 필요한 부분이다.

- 플랫폼: React Native + Expo SDK 51, expo-router (파일 기반 라우팅)
- 백엔드: Firebase (Firestore · Auth · Cloud Functions)
- 화면 코드 약 18,000줄 / 소스 104개
- 언어: 한국어 전용. 다국어 계획 없음

---

## 1. 이 앱은 무엇인가

**한국의 동호인 테니스 클럽을 운영하는 앱이다.**

한국 테니스 클럽은 보통 이렇게 굴러간다. 회원 30~80명, 주 2~3회 정기 운동,
코트장 한두 곳. 총무 한 명이 회비를 걷고, 엑셀로 명단을 관리하고, 단톡방에
공지를 올리고, 코트에 나와서 종이에 대진을 적는다. **그 총무가 그만두면
클럽이 휘청인다.**

이 앱은 그 일을 대신한다. 경쟁 상대는 다른 앱이 아니라 **카카오톡 단톡방 +
엑셀 + 종이**다. 그래서 기준은 "예쁜가"가 아니라 **"단톡방보다 편한가"**다.

### 설계에 계속 영향을 주는 조건

| 조건 | UI에 미치는 영향 |
|---|---|
| 주 사용자가 **40~60대** | 글자를 작게 쓸 수 없다. 탭 영역을 좁게 쓸 수 없다. 아이콘만으로 뜻을 전달할 수 없다 — 글자를 함께 둔다 |
| **야외 코트**에서 쓴다 | 햇빛 아래 본다. 저채도 회색 글씨는 안 보인다. 한 손으로 쓴다 |
| 총무 1명 : 회원 N명 | 화면이 **두 종류**여야 한다. 운영진이 보는 화면과 회원이 보는 화면이 다르다 |
| 돈을 다룬다 (회비) | 실수가 사람 사이의 문제가 된다. **되돌릴 수 없는 동작은 반드시 한 번 확인**한다 |
| 총무는 바뀐다 | 인수인계가 기능이다. "기록은 남고 권한만 넘어간다" |

### 핵심 사용 흐름 하나

> 화요일 저녁 7시 정기 운동.
> 총무가 일정을 만든다 → 회원들이 참석 투표를 누른다 → 화요일 저녁, 코트에서
> 총무가 [대진 생성]을 누른다 → 참석한 사람으로 복식 대진이 자동으로 짜인다 →
> 경기 결과를 입력한다 → 랭킹과 출석률이 자동으로 갱신된다 → 월말에 회비
> 미납자에게 알림이 나간다.

**이 한 줄이 앱의 척추다.** 다른 기능은 전부 이 흐름의 곁가지거나, 이 흐름을
가능하게 하는 준비물이다.

## 2. 사람 — 역할과 모드

### 클럽 안의 역할 5단계

권한이 넓은 순서다. `src/lib/constants.js`의 `ROLES`.

| 역할 | 할 수 있는 것 |
|---|---|
| **회장** | 모든 권한 + 역할 임명 (임명은 회장만) |
| **총무** | 운영 전반 + **회비·지출** |
| **운영진** | 일정·대진·회원 운영 (회비는 못 봄) |
| **리드** | **내가 맡은 코트장만** 운영 |
| **회원** | 조회 + 본인 참석 체크 |

돈을 보는 선이 **회장·총무**에서 끊긴다. 운영진이 일정은 짜도 남의 회비
납부 여부는 못 본다. 이건 권한 설계이자 **UI 설계**다 — 회비 메뉴 자체가
안 보인다.

### 보기 모드 (viewMode)

운영진이 **"회원에게는 이 화면이 어떻게 보이나"**를 직접 확인할 수 있다.
홈 화면 상단에서 `운영진 모드 / 리드 모드 / 회원 모드`를 전환한다.

> ⚠️ 이건 편의 기능이 아니라 **안전장치**다. 운영진은 자기 화면만 보므로,
> 회원 화면이 깨져 있어도 아무도 모른 채 몇 달이 간다. 전환 버튼이 그걸 막는다.
> 단, 모드를 바꿔도 **실제 권한은 안 바뀐다** (역할 임명은 여전히 불가).

### 앱 운영자 (isAppAdmin)

클럽 운영진과 **전혀 다른 축**이다. 서비스 자체를 운영하는 사람 — 코치 영상
승인, 광고비 장부, 공개 대회 등록. 클럽 회장이라도 여기엔 못 들어온다.
메뉴 묶음을 아예 따로 뒀다.

## 3. 화면 지도

### 3-1. 앱 전체 흐름

```
app/_layout.jsx              전역 상태(AppCtx) · 로그인 감시 · 라우팅 결정
   │
   ├─ 로그인 안 됨 ────────→  app/login.jsx        로그인 / 회원가입
   │                          app/join.jsx         초대 링크로 들어온 경우
   │
   ├─ 로그인됨 + 클럽 없음 ─→  app/onboarding.jsx  클럽 만들기 / 찾아 가입
   │
   └─ 로그인됨 + 클럽 있음 ─→  app/(tabs)/         본 앱
```

### 3-2. 하단 탭 5개

탭은 **매일 여는 것**만 둔다. 나머지는 전부 [더보기] 안으로.

| 탭 | 파일 | 누가 매일 쓰나 |
|---|---|---|
| **홈** | `(tabs)/index.jsx` | 전원 — 오늘 뭐 있지 |
| **일정** | `(tabs)/schedule.jsx` | 전원 — 참석 투표 |
| **대진** | `(tabs)/match.jsx` | 코트에서 운영진 |
| **레벨업** | `(tabs)/levelup.jsx` | 가끔 — 원포인트 / 용품 / 코치 (위쪽 칸 나누기) |
| **더보기** | `(tabs)/more.jsx` | 허브 |

> 랭킹은 탭에서 뺐다(`href: null`). 탭 7개는 한 줄에 너무 빽빽하다.
> 용품·원포인트도 따로 두면 6개라 휴대폰 권장(5개)을 넘었다. 「레벨업」 한 칸으로
> 합치고 더보기의 코치 찾기도 옮겼다. 이름을 정한 이유는 FEATURES.md 4장.
>
> 레벨업의 머리는 `src/components/LevelupTop.jsx` 하나 — 칸 나누기(높이 56, 칸 48)가
> 화면 첫 줄이고, 오른쪽에 등록 ＋ 버튼(56×56)이 붙는다(원포인트: 앱 관리자·승인 코치,
> 용품: 앱 관리자). 원포인트는 `src/components/onepoint/`(판단은 `src/lib/onepoint.js`),
> 용품·코치도 같은 부품(검색창·선반·칩 한 줄·빈 상태, `onepoint/parts.jsx`)을 쓴다.
> 용품의 판단은 `src/lib/gearView.js`.

### 3-3. [더보기] — 허브 구조

**30개 가까운 화면이 여기 한 파일 안에 산다.** `more.jsx`가 `sub` 상태 하나로
어떤 화면을 그릴지 정하고, 각 화면은 `src/components/*Screen.jsx`다.

```
더보기
├─ 내 활동      약관·개인정보 / 내 회비 / 내 기록·랭킹 / NTRP 등급
├─ 클럽 활동    클럽 대회 / 클럽 교류전 / 참가투표 / 공지·자유글 / 채팅 / 회원 목록
├─ 찾아보기     게스트 모집 / 코트 검색 / 코치 찾기 / 대회 찾기
├─ 앱 운영      코치 승인·광고비 / 앱 운영 관리          ← 앱 운영자만
└─ 클럽 운영    가입 신청 / 초대 / 출석 / 회비·지출 / 입금 대사 /
                회비 알림 / 결산 / 인수인계 / 코트장 / 페어 /
                대진 설정 / 클럽 설정                    ← 운영진만
                          (회비 계열 4개는 회장·총무만)
```

> ⚠️ **이 구조가 검토 대상이다.** 메뉴 하나에 30개가 매달려 있고, 라우팅이
> `switch(sub)` 한 덩어리다(`more.jsx` 481줄). 9장 참고.

### 3-4. 화면 이름은 한 곳에서만 정한다

`src/lib/constants.js`의 `SCREEN` 객체가 **모든 화면 이름의 유일한 출처**다.

안내 문구에서 다른 화면을 가리킬 때는 `[회원 목록]`처럼 대괄호로 적고,
`scripts/test-labels.mjs`가 **"문구가 가리키는 메뉴가 실제로 있는가"**를
자동으로 대조한다.

> 실제로 있었던 사고: 홈에 "운영진이 [회원] 화면에서…"라고 적었는데 실제
> 메뉴는 [회원 목록]이었다. 회원은 그 메뉴를 찾다가 포기한다. 코드가 도는
> 데는 지장이 없어서 아무도 모른다. 그래서 검사로 막는다.

## 4. 기능들이 어떻게 엮이는가

이 앱의 기능은 독립적이지 않다. **하나가 다음 것의 입력이 된다.**

### 4-1. 중심 사슬 — 모임에서 랭킹까지

```
  [일정] 모임 생성            운영진이 날짜·코트장·시간을 정한다
        │                     meetings/{id}
        ↓
  [일정] 참석 투표            회원이 직접 누른다 (본인 것만)
        │                     meetings/{id}.rsvp[uid]
        ↓
  [대진] 대진 생성            참석자만으로 복식 조합을 자동 생성
        │                     KDK · 청백전 · 리그 방식 선택
        │                     ⚠️ 고정 페어 · 성별 · NTRP 등급을 반영
        ↓
  [대진] 결과 입력            코트에서 그 자리에 입력
        │                     meetings/{id}.games[]
        ↓
  ├─→ [랭킹]     승·패·승률 집계
  ├─→ [출석]     참석률 집계
  └─→ [인수인계] 총무가 바뀌어도 이 기록은 남는다
```

**투표가 대진의 입력이고, 대진 결과가 랭킹의 입력이다.** 그래서 참석 투표를
안 받으면 대진을 짤 수 없고, 결과를 안 넣으면 랭킹이 0이 된다. UI는 이
의존을 계속 드러내야 한다 — 빈 화면에 "왜 비었는지"를 적는 이유다.

### 4-2. 돈의 흐름

```
  [클럽 설정] 회비 규칙        월 얼마 · 며칠까지 · 어느 계좌
        │                      ⚠️ 코트장별로 다르게 할 수 있다 (4-4)
        ↓
  [회비·지출] 이번 달 청구      회원별 납부/미납
        │
        ├── [입금 대사]        은행 거래내역을 붙여넣으면 입금자명을
        │                      회원과 자동으로 맞춰 준다
        │                      → 총무의 제일 큰 수작업이 여기였다
        │
        ├── [회비 알림]        미납자에게만 개별 발송 (단톡방 공개 독촉 대체)
        │                      → Cloud Function이 매일 자동 발송도 한다
        │
        └── [결산]             총회 자료 자동 생성
        ↓
  [내 회비]  회원이 보는 쪽 — 내 납부 현황만
```

> 회비는 **단톡방에서 가장 불편한 일**이다. "○○님 회비 입금 부탁드립니다"를
> 50명이 보는 곳에 올리는 것 말이다. 개별 알림으로 대체하는 것이 이 기능의
> 존재 이유이고, UI도 그 선을 지켜야 한다.

### 4-3. 클럽 밖으로 나가는 기능들

| 기능 | 범위 | 왜 분리돼 있나 |
|---|---|---|
| **게스트 모집** | 모든 클럽 공용 게시판 | 인원이 빌 때 외부에서 채운다 |
| **클럽 교류전** | 클럽 ↔ 클럽 | 상대 클럽을 검색해 초대. 명단은 1년 뒤 자동 익명화 |
| **코트 검색** | 전국 공공·사설 코트 | 공공데이터 기반 |
| **코치 찾기** | 지역별 코치 + 레슨 영상 | **이 앱의 수익모델** (코치 광고비) |
| **대회 찾기** | 협회·지자체 주최 대회 | ⚠️ **클럽 일정과 절대 섞지 않는다** (아래) |

> ⚠️ **[클럽 대회]와 [대회 찾기]는 다른 물건이다.**
> - **클럽 대회** = 우리끼리 여는 월례대회. 참가자가 우리 회원이고 대진도
>   우리가 짠다. **일정에 함께 뜬다.**
> - **대회 찾기(공개 대회)** = KTA·시도협회가 여는 큰 대회. 우리가 여는 게
>   아니라 "이런 게 열린다"를 알려 주는 것. **일정에 절대 안 들어간다.**
>
> 섞으면 안 되는 이유: 전국 대회는 한 달에 수십 건인데 우리 클럽 일정은
> 여덟 번이다. 섞으면 우리 일정이 묻히고, 달력은 거의 모든 날에 점이 찍혀
> 쓸모가 없어진다. 일정 화면에는 **"이 달 우리 지역 N건"이라는 한 줄만** 둔다.

### 4-4. 하이어라키 — 전체 ↔ 코트장

클럽이 코트장을 여러 곳 쓰면, 코트장마다 회비도 알림도 달라진다.

```
클럽 전체 설정  ← 기본값
      ↑ 덮어씀
코트장별 설정   ← 이 코트장만 다르게 (비워 두면 클럽 값을 따른다)
```

`src/lib/scope.js`가 이 규칙의 유일한 구현이다. UI에서는 코트장 화면의
**"이 코트장만 다르게"** 패널이 이걸 드러낸다.

> ⚠️ 빈 문자열 = "설정 안 함"이고 `0`은 진짜 값이다(회비 0원인 코트장이
> 있을 수 있다). 이 구분이 무너지면 회비가 조용히 두 번 청구된다.

### 4-5. 상태를 나르는 길

```
app/_layout.jsx  ─ AppCtx ─→  clubId, me, viewMode, venueId, isAppAdmin
                                    │
src/hooks/useClub.js ───────────────┤  Firestore 실시간 구독을 한 곳에서
                                    │  club, members, meetings, fees,
                                    │  venues, posts, polls, …
                                    │  + 권한 계산(isAdmin, seeFees, …)
                                    ↓
                              각 화면은 props 로 받아 쓴다
```

화면은 **직접 Firestore를 부르지 않는다.** `useClub`이 구독하고 계산해서
내려 준다. 권한 판단(`isAdmin`, `seeFees`, `canAppoint`)도 여기서 한 번만 한다.

> ⚠️ 모임 구독은 **최근 12개월 + 미래 전부**로 잘라 뒀다. 주 2회 × 2년이면
> 200건이 넘고 앱을 켤 때마다 다 읽기 때문이다. 대신 **그보다 오래된 랭킹을
> 보려 하면 화면이 "눌러야 불러옵니다"라고 말한다** — 말없이 0을 보여 주면
> 아무도 잘렸다는 걸 모른다.

## 5. 디자인 시스템 — 토큰

`src/lib/theme.js` 한 파일이 전부다. 모든 화면이 여기서만 값을 가져온다.

### 5-1. 색

```js
/* 브랜드 */
ink:       #1A2B24   // 다크 카드 배경 — 그린 기 도는 차콜
green:     #0E6B4F   // 주 액션
green2:    #0D8A66   // 링크·보조 강조
greenSoft: #EAF4EF   // 선택 배경·아이콘 틴트
lime:      #8FD6B8   // 다크 카드 위 포인트 텍스트
lime2:     #BFE3D3   // 다크 카드 위 보조

/* 중립 */
bg:      #F4F5F7     // 화면 배경
surface: #FFFFFF     // 카드
text:    #1B1F27     // 본문 (거의 검정)
sub:     #5B6470     // 보조
faint:   #98A0AB     // 흐림·플레이스홀더
border:  #E9EBEE
fill:    #F2F3F5     // 입력창·비활성

/* 상태 */
danger #D6455D / dangerBg #FBEDF0
warn   #B97D26 / warnBg   #FAF3E4
info   #3563D9 / infoBg   #EFF3FC

/* 성별 구분 — 대진표에서 */
male   #3A5FA8 / maleBg   #EEF2F9
female #B04A66 / femaleBg #F9EFF2
```

**색 규칙 3가지**

1. 색은 두 가지뿐 — **짙은 그린(브랜드) + 차콜/그레이(중립)**. 나머지는 전부 상태색.
2. **위계는 색이 아니라 굵기·크기로** 만든다. 중요한 걸 색으로 칠하지 않는다.
3. 상태색은 **의미가 있을 때만** 쓴다. 빨강은 "문제"일 때만 — 장식으로 쓰면
   진짜 문제가 안 보인다.

### 5-2. 타이포

```js
h1       22 / 700 / -0.4
h2       18 / 700 / -0.3
h3       15 / 700 / -0.2
body     14 / 400
bodyBold 14 / 600
label    12 / 600  (C.sub)
caption  11.5 / 400 (C.faint)
num      20 / 700 / -0.5   // 숫자 요약
```

**굵기 800을 넘지 않는다.** 900은 쓰지 않는다 — 한글에서 900은 뭉툭하게
뭉쳐 보인다.

### 5-3. 간격 · 모서리 · 그림자

```js
S = { xs:4, sm:8, md:12, lg:16, xl:20, xxl:28 }
R = { sm:8, md:12, lg:14, xl:18, pill:999 }
SHADOW = { sm, md, lg }   // 전부 옅다. shadowOpacity 0.04 ~ 0.10
TAB_BAR_SPACE = 78        // 스크롤 끝 여백 (마지막 카드가 탭바에 가리지 않게)
```

테두리 대신 **옅은 그림자**로 카드를 띄운다. 화면 배경이 회색(`bg`)이라
흰 카드가 자연히 떠 보인다.

## 7. 화면 패턴

### 7-1. 표준 화면 골격

```jsx
<View style={{ flex: 1, backgroundColor: C.bg }}>
  <ScreenHeader title="…" subtitle="…" onBack={…} right={…} />
  <ScrollView contentContainerStyle={{ padding: 16, paddingBottom: bottomPad }}>
    <SectionTitle>구역</SectionTitle>
    <Card>…</Card>
  </ScrollView>
  {toast && <Toast />}
</View>
```

- **헤더는 흰 배경 + 얇은 경계선.** 예전엔 헤더 전체가 딥그린이었는데
  화면마다 큰 색 덩어리가 얹혀 무겁고 예스러웠다.
- **뒤로가기는 두 플랫폼 모두 화면 안에 둔다.** iOS엔 하드웨어 키가 없고,
  안드로이드도 화면 안 버튼이 한 손으로 쓰기 편하다. 안드로이드 하드웨어
  키는 같은 핸들러에 연결한다.
- `paddingBottom`에 **탭바 높이 + 세이프에어리어**를 더한다.

### 7-2. 피드백

| 상황 | 방법 |
|---|---|
| 성공·안내 | **토스트** — 화면 하단, 다크 알약 |
| 입력 오류 | 필드 바로 아래 빨간 글씨 |
| 화면 단위 오류 | 색 있는 **배너** (아이콘 + 문장) |
| 되돌릴 수 없는 동작 | `Alert.alert` 확인 |
| 빈 상태 | `EmptyState` — **"왜 비었는지 + 뭘 하면 되는지"** |

> 빈 화면에 "데이터가 없습니다"만 쓰지 않는다. 대부분 비어 있는 건 앞 단계를
> 안 했기 때문이라, 그 앞 단계로 가는 길을 함께 둔다.

### 7-3. 로그인 화면 (2026-09-18 새로 만듦)

`app/login.jsx`가 최근 손본 화면이라 현재 기준에 가장 가깝다. 검토 시작점으로
좋다.

- 밝은 배경 + 떠 있는 흰 카드 (앱 안쪽과 톤이 이어진다)
- 키보드 회피 + 스크롤
- 비밀번호 보기/가리기, 비밀번호 재설정
- **회원가입 시 약관 동의 필수**, 전문은 그 자리에서 모달로
- 소셜 로그인 버튼은 **준비된 것만** 그린다 (지금은 키가 없어 0개)

## 8. 지금까지 내린 결정과 이유

디자인 토큰은 v3까지 왔다. **왜 바꿨는지**가 검토에 도움이 될 것이다.

| 버렸다 | 이유 |
|---|---|
| 형광 라임(#bef264)을 배지·글자에 넓게 | 화면이 형광으로 들떴다. 저채도 민트로 교체 |
| `fontWeight: 900` 남발 | 숫자·제목이 뭉툭하게 뭉쳐 보였다. 800 상한 |
| UI 아이콘에 이모지 | 기기·OS마다 모양이 제각각. 상용 앱은 안 그런다 |
| 헤더 전체 딥그린 | 큰 색 덩어리가 무겁고 예스러웠다 |
| 카드의 두꺼운 테두리 | 옅은 그림자로 교체 |
| 그린 위 라임 버튼 | 대비가 낮았다. 딥그린 + 흰 글씨로 |

## 9. 우리가 약하다고 보는 곳 — **검토가 가장 필요한 부분**

솔직하게 적는다. 여기에 의견을 주시면 가장 도움이 된다.

### 9-1. 정보 구조 (가장 큰 문제)

- **[더보기]에 30개가 매달려 있다.** 5개 묶음으로 나눴지만 여전히 길다.
  운영진은 스크롤을 한참 내려야 [클럽 설정]에 닿는다.
- 홈 화면이 **모든 것의 요약**이 되려다 보니 길어졌다(584줄). 무엇을 홈에
  두고 무엇을 빼야 하는가.
- `more.jsx`가 **라우터 겸 화면**이다(481줄, `switch(sub)` 한 덩어리).
  구조적으로 맞는가.

### 9-2. 화면 밀도

- 대진표(`match.jsx`, 1117줄)가 가장 복잡하다. **코트에서 서서 한 손으로**
  쓰는 화면인데 지금 밀도가 맞는지 확신이 없다.
- 일정 화면이 목록/달력 두 모드를 다 갖고 있다. 전환 UI가 충분히 눈에 띄는가.
- 표가 많다. 40~60대가 야외에서 읽기에 글자가 충분히 큰가.

### 9-3. 시각적 완성도

- **브랜드가 약하다.** 로고랄 게 없고, 색 하나(딥그린)로 버티고 있다.
- **일러스트·빈 상태 그래픽이 전혀 없다.** 전부 글자와 아이콘이다.
- 애니메이션·전환 효과가 없다. 화면이 툭툭 바뀐다.
- 다크 모드가 없다 (야간 실내 코트를 생각하면 필요할 수도).

### 9-4. 접근성

- 대비를 체계적으로 검증한 적이 없다. 특히 `C.faint`(#98A0AB) 위 작은 글씨.
- 글꼴 크기 확대 설정(기기 접근성)에서 레이아웃이 깨지는지 확인 안 함.
- 스크린 리더 라벨이 일부 컴포넌트에만 있다.

### 9-5. 일관성

- 화면이 30개가 넘는데 **같은 뜻을 다르게 그린 곳**이 있을 것이다.
  (예: 어떤 화면은 `Chip`으로 상태를, 어떤 화면은 색 글씨로)
- 최근 만든 화면(로그인, 대회 찾기)과 초기 화면(대진, 회비) 사이에
  세대 차이가 있다.

## 부록 — 검토자에게 드리는 부탁

이 앱은 **예쁨보다 "단톡방보다 편한가"**로 판단해야 합니다. 그래서:

- "요즘 앱 같지 않다"는 지적은 환영합니다. 다만 **40~60대가 야외에서 한 손으로**
  쓴다는 조건 위에서 봐 주시면 좋겠습니다.
- 글자를 줄이거나 여백을 크게 늘리는 제안은 그 조건과 충돌할 수 있습니다.
- **9장(약한 곳)에 대한 의견이 가장 필요합니다.** 특히 9-1 정보 구조.
- 색·타이포 체계를 통째로 바꾸는 제안도 괜찮습니다. `theme.js` 한 파일만
  고치면 모든 화면이 따라오도록 만들어 뒀습니다.
