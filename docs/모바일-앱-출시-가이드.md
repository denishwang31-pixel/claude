# 가계부 앱 — iOS / Android 스토어 출시 가이드 (하나부터 열까지)

이 문서는 **현재 이 저장소의 가계부 자동화 앱**(React + Vite 클라이언트, Express + tRPC 서버, **PostgreSQL**)을
그대로 활용해서 iOS 앱스토어와 Google Play에 출시하는 전체 과정을 순서대로 설명합니다.

> ⚠️ **DB 정정**: 이 앱의 실제 DB는 **PostgreSQL**입니다(`drizzle.config.ts` dialect=postgresql,
> `drizzle-orm/pg-core`, `@neondatabase/serverless`). `package.json`에 `mysql2`가 남아 있으나
> 실제로는 쓰이지 않는 잔재입니다. 아래 배포 설명도 Postgres 기준입니다.

> **핵심 요약**: 지금 앱은 "내 PC에서 서버와 DB를 켜야 도는 웹앱"입니다.
> 모바일 앱이 되려면 ① 서버와 DB를 인터넷(클라우드)에 올리고,
> ② 웹 화면을 **Capacitor**라는 도구로 앱 껍데기에 넣고,
> ③ 애플/구글 개발자 계정으로 심사를 받아 올리면 됩니다.
> 코드를 새로 짤 필요는 거의 없고, 지금 React 코드를 그대로 씁니다.

### 왜 Capacitor인가?

| 방식 | 설명 | 판단 |
|---|---|---|
| **Capacitor (추천)** | 지금의 React 웹앱을 그대로 네이티브 앱 껍데기에 넣음 | 코드 재사용 100%, 스토어 등록 가능 |

## 1단계. 서버와 DB를 클라우드에 배포

지금은 `가계부실행.bat`으로 내 PC에서 서버(포트 3001)와 **로컬 PostgreSQL**을 켜는 구조입니다.
앱 사용자는 내 PC에 접속할 수 없으므로, 서버와 DB가 **항상 켜져 있는 인터넷 주소**가 필요합니다.

### 1-0. "내 로컬 Postgres로 그대로 되나?" — 결론

- **개발/테스트**: 내 PC의 로컬 Postgres로 충분합니다(지금도 그렇게 동작).
- **앱 출시(실사용)**: ❌ 로컬 Postgres는 **그대로 못 씁니다.** 내 PC는 끄면 죽고, 공인 IP·고정
  주소·상시 가동이 없어 앱 사용자가 접속할 수 없습니다. → **클라우드 Postgres로 이전**해야 합니다.
- **좋은 소식**: DB 종류는 그대로 **PostgreSQL**이라, **코드 수정 0줄**로 접속 주소(`DATABASE_URL`)만
  클라우드 것으로 바꾸면 됩니다. 스키마도 `npm run db:push` 한 번으로 그대로 올라갑니다.

### 1-1. 추천 조합 (모두 PostgreSQL)

- **Neon** (https://neon.tech) — **가장 추천**. 이 앱이 이미 `@neondatabase/serverless`를 쓰므로
  궁합이 완벽. **무료 티어 0.5GB**로 가계부는 수년간 무료. 서버리스라 관리 부담 0.
- **Supabase** (https://supabase.com) — Postgres 무료 500MB + 인증/스토리지 부가기능.
- **Railway/Render** — Node 서버 + Postgres를 한곳에. 서버 배포까지 묶고 싶을 때. 월 $5 내외.
- 국내가 편하면 **Cloudtype** (https://cloudtype.io) — Postgres 지원.

> 구성 예: **DB = Neon(무료)** + **서버 = Render/Railway** 조합이 가장 저렴·간단합니다.

### 1-2. Neon 연결 — 처음 하는 사람용 아주 자세한 절차

**무엇을 하러 가는가?** Neon은 "인터넷에 항상 켜져 있는 PostgreSQL"을 무료로 주는 서비스입니다.
여기서 **접속 주소(Connection string) 하나**를 받아 우리 앱의 `DATABASE_URL`에 넣는 것이 전부입니다.

**① 가입**
1. https://neon.tech 접속 → 우측 상단 **Sign up**.
2. **Continue with GitHub**(또는 Google)로 가입하면 가장 빠릅니다. 이메일 인증만 하면 끝.

**② 프로젝트(=데이터베이스) 생성**
3. 로그인하면 **Create project** 화면이 나옵니다(안 나오면 좌상단 **Projects → New Project**).
4. 입력 항목:
   - **Project name**: 아무거나 (예: `household-budget`)
   - **Postgres version**: 기본값 그대로(16 등)
   - **Region**: 드롭다운에서 **Asia Pacific (Seoul)** 또는 **(Tokyo)** 선택 ← 한국에서 빠름
   - **Database name**: 기본 `neondb` 그대로 둬도 됨
5. **Create project** 클릭 → 몇 초 뒤 생성 완료.

**③ 접속 주소(Connection string) 복사 — 가장 중요**
6. 생성 직후 **Connection Details**(또는 대시보드 상단의 **Connect** 버튼) 상자가 보입니다.
7. 거기서 이런 형태의 문자열을 **Copy**:
   ```
   postgresql://neondb_owner:npg_XXXXXXXX@ep-cool-name-123456-pooler.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```
   - **드롭다운 옵션 주의**: **"Pooled connection"(권장)** 을 선택하세요(주소에 `-pooler`가 들어감).
     서버리스/동시접속에 안정적입니다.
   - **"Show password"** 를 켜야 비밀번호(`npg_...`)가 주소에 포함된 완전한 문자열이 나옵니다.
   - 이 비밀번호는 나중에 다시 못 보니, 이때 복사해두세요(잊으면 **Reset password**로 재발급).

**④ 우리 앱에 연결**
8. 이 주소를 **그대로** `DATABASE_URL`에 넣습니다. (드라이버가 `postgres://`·`postgresql://` 둘 다 인식)
   - 로컬 테스트: 프로젝트 루트 `.env` 파일의 `DATABASE_URL=...`
   - 배포 서버(Render/Railway): 환경변수 `DATABASE_URL`에 붙여넣기(1-3 참고)
   - ⚠️ 끝에 **`?sslmode=require`** 가 반드시 있어야 합니다(Neon은 SSL 필수). 복사본에 없으면 직접 추가.

**⑤ 테이블 만들기 (딱 한 번)**
9. 로컬에서 `.env`의 `DATABASE_URL`을 Neon 주소로 바꾼 뒤:
   ```bash
   npm install
   npm run db:push        # drizzle-kit 이 users/transactions/budgets 등 모든 테이블을 Neon에 생성
   ```
   - "changes applied" 비슷한 메시지가 나오면 성공. (앱 서버도 시작 시 `runAutoMigrations`로
     빠진 컬럼·테이블을 자동 보강하므로, 이 단계를 놓쳐도 서버가 한 번 뜨면 대부분 채워집니다.)

**⑥ 연결 확인**
10. Neon 대시보드 좌측 **Tables**(또는 **SQL Editor**)에서 `users`, `transactions`, `budgets`,
    `subscriptions`… 테이블이 보이면 연결 성공입니다.
    - SQL Editor에서 `SELECT * FROM users;` 실행해봐도 됩니다(처음엔 비어 있음).

**(선택) 내 로컬 데이터 옮기기**
11. 기존 로컬 Postgres 데이터를 가져오려면:
    ```bash
    pg_dump "postgres://budget:budget123@localhost:5432/household_budget" --no-owner --no-acl -f dump.sql
    psql "위에서 복사한 Neon 주소" -f dump.sql
    ```

> 💡 **비용**: 무료 티어(0.5GB, 프로젝트 1개)로 가계부는 수년간 충분합니다. 카드번호를 저장하는 게
> 아니라 텍스트 거래내역만 담기 때문입니다.
> 💤 **자동 절전**: 무료 Neon은 안 쓰면 잠들었다가 첫 요청 때 깨어납니다(수백 ms 지연). 정상입니다.

### 1-3. 서버 배포 절차 (Render/Railway 기준)

1. Render/Railway 가입 → New → **Deploy from GitHub repo** → 이 저장소 선택
2. 환경변수 설정 (`.env.example` 참고):
   ```
   DATABASE_URL=postgres://... (1-2에서 만든 Neon 주소, ?sslmode=require 포함)
   NODE_ENV=production
   SESSION_SECRET=아무도 못 맞출 긴 랜덤 문자열
   PORT=3001
   KAKAO_CLIENT_ID=... (카카오 로그인 쓸 경우)
   KAKAO_REDIRECT_URI=https://내서버주소/auth/kakao/callback
   DEV_AUTO_LOGIN=false   ← 반드시 false! (안 그러면 아무나 로그인됨)
   ```
3. 빌드 명령: `npm run build`, 시작 명령: `npm start`
4. 배포된 `https://내서버주소` 접속해 가계부가 뜨는지 확인

> **✅ 체크포인트**: 휴대폰 브라우저(LTE, 와이파이 끄고)에서 서버 주소로 접속해
> 엑셀 업로드까지 되면 1단계 성공입니다.

## 2단계. 앱용으로 코드 몇 군데 수정

Capacitor 앱은 화면을 `capacitor://localhost` (앱 내부)에서 열기 때문에,
"같은 주소의 서버"라는 가정이 깨집니다. 3곳을 고쳐야 합니다.
**(2-1, 2-2는 이 저장소에 이미 반영 완료 — 아래는 무엇이 어떻게 되었는지 설명입니다.)**

### 2-1. API 주소를 환경변수로 — ✅ [구현완료] (`client/src/lib/trpc.ts`)

상대 경로 `"/trpc"` → `VITE_API_URL` 기반 절대주소로 변경했습니다.
```ts
export const API_BASE = (import.meta.env.VITE_API_URL ?? "").replace(/\/+$/, "");
export function apiUrl(path: string) { return `${API_BASE}${path.startsWith("/") ? path : "/"+path}`; }
// httpBatchLink({ url: apiUrl("/trpc") }) 로 사용
```
- 웹/개발 빌드: `VITE_API_URL` 미설정 → 빈 값 → 기존처럼 상대경로 + vite 프록시로 동작(무변화).
- 앱 빌드: 루트의 **`.env.app.example`** 참고 → `.env.production` 에 `VITE_API_URL=https://내서버주소`
  넣고 `npm run build` → 앱 번들에 주입.
- `import.meta.env` 타입은 **`client/src/vite-env.d.ts`** 로 선언.

### 2-2. 서버 CORS와 세션 쿠키 — ✅ [구현완료] (`server/index.ts`, `server/_core/env.ts`)

- **CORS**: 앱 웹뷰 출처(`capacitor://localhost`, `http(s)://localhost`, `ionic://localhost`)를
  기본 허용 + 환경변수 **`CLIENT_ORIGINS`**(쉼표 구분)로 웹 도메인 추가 허용. 개발 환경은 전체 허용.
- **세션 쿠키**: 프로덕션에서 `secure: true` + `sameSite: "none"`(교차 출처 전송 허용), 개발에서는
  `sameSite: "lax"` + non-secure. 프록시(Render/Railway) TLS 종료 대응으로 `app.set("trust proxy", 1)` 추가.

> iOS 웹뷰가 교차 출처 쿠키를 막아 로그인 유지가 안 되면, `capacitor.config.ts`에서 앱 출처를
> 서버와 맞추거나 세션 대신 **토큰(Authorization 헤더) 방식**으로 바꾸는 것이 가장 확실합니다(2-3 참고).

### 2-3. 로그인 방식 — ✅ [구현완료] 이메일 + 카카오/구글/네이버

이메일/비밀번호 **회원가입·로그인** + **카카오·구글·네이버 소셜 로그인**을 모두 구현했습니다.

**구현 내용**
- **인증 게이트**: 이제 로그인해야 앱을 볼 수 있습니다. `client/src/components/AuthGate.tsx`가
  `me` 조회로 로그인 여부를 판별 → 미로그인 시 `pages/Login.tsx`(로그인/회원가입 + 소셜 3종 버튼).
- **서버**(`server/index.ts`):
  - `POST /auth/register` — 이메일 형식·비번 8자 검증 → **scrypt** 해시(`server/_core/password.ts`,
    외부 라이브러리 없이 Node 내장 crypto) → 사용자 생성 → 세션 로그인.
  - `POST /auth/login` — 비번 검증(계정 존재 여부 비노출 메시지).
  - `GET /auth/kakao|google|naver (+/callback)` — OAuth 리다이렉트, `state`로 CSRF 방지(구글·네이버).
  - `POST /auth/logout` — 세션 파기(헤더에 로그아웃 버튼 추가).
- **DB**: `users`에 `passwordHash` 컬럼 추가, `openId` 길이 확장(자동 마이그레이션). 이메일 계정 openId =
  `email:<email>`, 소셜 = `kakao:/google:/naver:<id>`.
- **게이트 강화**: `server/_core/trpc.ts` — 프로덕션에서는 세션이 없으면 보호 API가 `UNAUTHORIZED`.
  개발 자동로그인은 `NODE_ENV≠production && DEV_AUTO_LOGIN=true`일 때만.

**소셜 로그인 제공자 설정** (쓰는 것만 `.env`에 채우면 됨 — `.env.example` 참고)
| 제공자 | 발급처 | 콜백(리디렉션) URI 등록 |
|---|---|---|
| 카카오 | developers.kakao.com (REST API 키) | `https://내서버/auth/kakao/callback` |
| 구글 | console.cloud.google.com (OAuth 2.0 클라이언트) | `https://내서버/auth/google/callback` |
| 네이버 | developers.naver.com (네이버 로그인) | `https://내서버/auth/naver/callback` |

각 제공자 콘솔에 위 **콜백 URI를 정확히 등록**해야 합니다(로컬 테스트는 `http://localhost:3001/...`).

**앱(네이티브)에서 소셜 로그인 주의**
- 소셜은 서버가 제공자로 리다이렉트합니다. 앱 웹뷰에서 로그인 후 앱으로 복귀시키려면
  `AUTH_SUCCESS_REDIRECT`를 앱 딥링크 스킴(예: `budgetapp://auth`)으로 바꾸고,
  Capacitor의 `appUrlOpen` 리스너로 복귀를 처리하면 됩니다(딥링크 설정은 3단계 이후 작업).
- **가장 확실한 앱 경험**: 이메일 로그인은 앱 안에서 그대로 동작하므로, 앱 초기 버전은
  **이메일 로그인 위주 + 소셜은 웹**으로 시작하고 딥링크는 후속으로 붙이는 것을 권장합니다.

**애플 규정 4.8 대응 — ✅ Apple 로그인 구현완료**: 카카오/구글/네이버와 함께 **Apple로 로그인**도
넣었습니다(로그인 화면 4번째 버튼). Apple은 client_secret을 **ES256 JWT로 서명**해야 하는 특수
방식이라 `server/_core/appleAuth.ts`에서 Node 내장 crypto로 직접 생성하고, 콜백은 form POST
(`response_mode=form_post`)로 받습니다.
- 설정: developer.apple.com → **Services ID**(=`APPLE_CLIENT_ID`), **Sign in with Apple Key(.p8)**
  발급 → `APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY`(.p8 내용, 줄바꿈을 `\n`으로) 채우기.
- ⚠️ Apple은 **https 실도메인 콜백만 허용**(localhost 불가) → 배포 후 테스트 가능.
- iOS 네이티브 앱에서는 웹 리다이렉트 대신 **네이티브 Apple 로그인 플러그인**
  (`@capacitor-community/apple-sign-in`)을 쓰는 것이 UX가 더 좋습니다(후속 작업).

## 5단계. Android — 서명 키와 릴리스 빌드(AAB) · 처음 하는 사람용

> 목표: 구글 플레이에 올릴 **`app-release.aab`** 파일 하나를 만드는 것. 처음이면 순서대로 그대로 따라오세요.

### 5-0. 준비물 설치 (한 번만)

1. **Android Studio 설치**: https://developer.android.com/studio → 다운로드 → 설치.
   설치 중 "Android SDK", "Android SDK Platform", "Android Virtual Device"는 **체크된 채로** 진행.
2. **JDK**: Android Studio에 내장된 JDK를 쓰면 되므로 따로 설치 안 해도 됩니다.
3. 이 프로젝트를 준비:
   ```bash
   npm install
   npm run build          # 웹 자산 빌드
   npx cap add android    # android/ 폴더 생성 (3단계에서 이미 했다면 생략)
   npm run cap:sync       # 웹 빌드를 android 프로젝트로 복사
   ```
4. Android Studio 실행 → **Open** → 이 프로젝트의 **`android`** 폴더를 선택해 엽니다.
   처음 열면 Gradle 동기화에 몇 분 걸립니다(하단 진행바가 끝날 때까지 대기).

### 5-1. 서명 키(keystore) 만들기 — 평생 1개, 절대 분실 금지

앱은 "서명 키"로 서명해야 스토어에 올라갑니다. **이 키를 잃으면 그 앱을 영영 업데이트 못 합니다.**

**방법 A — Android Studio 화면으로(초보 추천)**
1. 상단 메뉴 **Build → Generate Signed Bundle / APK…**
2. **Android App Bundle** 선택 → **Next**
3. **Key store path** 오른쪽 **Create new…** 클릭 → 새 창에서:
   - **Key store path**: 안전한 위치에 `budget-release.jks`로 저장(예: 문서 폴더). **프로젝트 밖**에 두세요.
   - **Password / Confirm**: keystore 비밀번호(메모 필수)
   - **Alias**: `budget` (원하는 이름)
   - **Key Password**: 키 비밀번호(메모 필수, keystore 비번과 같아도 됨)
   - **Validity (years)**: `25` 이상
   - **Certificate**: 이름/조직 대충 입력(공개 안 됨) → **OK**
4. 만들어진 정보로 다음 화면에서 서명 → (5-2로 이어짐)

**방법 B — 명령어로**
```bash
keytool -genkey -v -keystore budget-release.jks \
  -alias budget -keyalg RSA -keysize 2048 -validity 10000
# 묻는 것: keystore 비번 → 이름/조직(대충) → 키 비번. 전부 메모.
```

> ⚠️ **`*.jks` 파일 + 두 비밀번호 + alias**를 클라우드 드라이브 등 **2곳 이상 백업**하세요.
> git에는 **절대 커밋 금지**(이미 `.gitignore`에 `*.jks`/`*.keystore` 등록됨).

### 5-2. AAB 빌드 (두 가지 방법 중 택1)

**방법 A — Android Studio 화면(초보 추천)**
1. **Build → Generate Signed Bundle / APK… → Android App Bundle → Next**
2. 5-1에서 만든 keystore 선택 + 비밀번호/alias 입력 → **Next**
3. **Build Variants: release** 선택 → **Create/Finish**
4. 완료 팝업의 **locate** 클릭 → 파일 위치로 이동:
   `android/app/release/app-release.aab` (또는 `.../build/outputs/bundle/release/app-release.aab`)

**방법 B — 명령어(자동화용)**
서명 정보를 gradle에 알려줘야 합니다. `android/keystore.properties` 파일을 만들고:
```properties
storeFile=/절대경로/budget-release.jks
storePassword=키스토어비밀번호
keyAlias=budget
keyPassword=키비밀번호
```
`android/app/build.gradle`의 `android { }` 안에 서명 설정 추가:
```gradle
def kp = new Properties()
def kpFile = rootProject.file("keystore.properties")
if (kpFile.exists()) kp.load(new FileInputStream(kpFile))

android {
  signingConfigs {
    release {
      storeFile file(kp['storeFile']); storePassword kp['storePassword']
      keyAlias kp['keyAlias']; keyPassword kp['keyPassword']
    }
  }
  buildTypes { release { signingConfig signingConfigs.release } }
}
```
그런 다음:
```bash
cd android && ./gradlew bundleRelease
# → android/app/build/outputs/bundle/release/app-release.aab
```
> `keystore.properties`도 비밀이므로 커밋 금지(`.gitignore`에 추가하세요).

### 5-3. 버전 관리 (업데이트할 때마다 필요)

`android/app/build.gradle`의 `defaultConfig`에서 **매 업로드마다 올려야** 합니다:
```gradle
versionCode 2        // 정수, 반드시 +1씩 증가 (같으면 업로드 거부)
versionName "1.0.1"  // 사용자에게 보이는 버전
```

> 구글은 **AAB**(App Bundle)를 받습니다(APK 아님). 실제 사용자에게 전달되는 APK는 구글이 자동 생성하고
> **Play 앱 서명(Play App Signing)** 으로 다시 서명합니다 — 최초 업로드 시 동의하면 됩니다.

**✅ 5단계 성공**: `app-release.aab` 파일이 손에 있으면 6단계(Play Console 업로드)로 갑니다.

2. Xcode에서 프로젝트 선택 → **Signing & Capabilities** 탭:
   - Team: 본인 개발자 계정 선택
   - Bundle Identifier: 3단계의 앱 ID와 동일하게
   - "Automatically manage signing" 체크 → 인증서·프로비저닝 자동 처리
3. 실기기 테스트: 아이폰 USB 연결 → 상단 기기 선택 → ▶
4. 배포용 빌드: 상단 기기를 **Any iOS Device (arm64)** 로 → 메뉴 **Product → Archive**
5. Archive 완료 창에서 **Distribute App → App Store Connect → Upload**

## 8단계. App Store Connect 등록과 심사

1. https://appstoreconnect.apple.com → **나의 앱 → + 신규 앱**
   (이름, 번들 ID, SKU 입력)
2. **TestFlight**: 업로드된 빌드로 가족·지인에게 먼저 배포해 테스트 (이메일 초대, 최대 1만 명, 심사 없이 내부 테스터 100명)
3. **앱 정보 입력**:
   - 스크린샷: 6.7인치(1290×2796) 필수, 가능하면 6.5/5.5인치도
   - 개인정보처리방침 URL, **앱 개인정보 보호(누트리션 라벨)**: 수집 항목 사실대로 (금융 정보, 식별자 등)

4. **심사 제출 시 메모**: 심사원이 로그인할 수 있도록 **데모 계정(아이디/비번)을 반드시 제공**
   + 사용법 요약("은행 엑셀 파일을 업로드하면 자동 분류됩니다. 샘플 파일: ~") 첨부
5. 심사: 보통 24~48시간. 거절되면 사유가 오고, 수정 후 재제출하면 됩니다.

# 제품 로드맵 (자동분류·데이터수집·락인·보안)

이 섹션은 "출시"를 넘어 **경쟁력 있는 무료 가계부**로 키우기 위한 기능 로드맵입니다.
각 항목에 **[구현완료] / [설계] / [외부연동]** 상태를 표기했습니다.

## R1. 일반 카드/은행 파일 자동 분류 — [구현완료]

### 무엇이 되었나
뱅크샐러드처럼 "대분류"가 이미 붙은 파일이 아니라, **카드사/은행에서 바로 받은
가맹점명만 있는 내역**도 자동 분류됩니다. `내용(content)`에 들어있는 가맹점명·키워드로
카테고리를 추정합니다.

- `스타벅스`→카페, `이마트·CU·GS25`→식비, `배달의민족`→외식&배달,
  `카카오택시·○○운수`→교통비, `SK주유소`→차량유지비, `넷플릭스`→구독비,
  `올리브영`→미용, `한국전력`→공과금, `삼성생명`→보험, `급여`→근로소득 … (649개 키워드)

### 어떻게 동작하나 (코드)
- **키워드 사전**: `shared/keywordCategories.ts` — 25개 카테고리 그룹, 649개 키워드.
  배열 순서 = 우선순위(구체적 브랜드 위 → 포괄 단어 아래). 부분일치(LIKE).
- **분류 우선순위** (`server/db.ts`의 `buildEffectiveCategoryExpr`):
  ```
  ① 수동지정 customCategory
  ② 학습된 규칙  ruleCategory
  ③ 자동분류 autoMapSQL = 뱅크샐러드 대분류 매핑 → 내용 키워드 매핑 → 기타_기타
  ④ 원본 category
  ```
  뱅크샐러드 파일은 ③의 대분류 매핑으로, 일반 파일은 ③의 **키워드 매핑**으로 분류됩니다.
- 키워드 매핑은 읽기 쿼리에 SQL `CASE`로 인라인되어 **규칙 재계산(baking) 없이 즉시 적용**됩니다.

### 가맹점↔업종 공개 데이터셋이 있나? (사용자 질문)
결론: **완전 정리된 무료 공개 데이터는 없습니다.**
- 여신금융협회 "가맹점 표준업종 코드"(MCC 유사)는 코드 체계일 뿐 상호명 매핑이 아님.
- 공공데이터포털 "소상공인 상가업소 정보"(소진공)는 상호·업종이 있으나 카드 승인 상호명과
  표기가 달라 매칭 정확도가 낮음.
- **현실적 표준 방식** = 지금처럼 대표 브랜드/업종 키워드를 직접 관리 + 사용자가 고친 결과를
  규칙(`category_rules`)으로 학습(이미 `generateRulesFromTransactions`로 구현됨).
  키워드는 `shared/keywordCategories.ts`에 계속 추가하면 됩니다.

### 일반 파일 열 매핑 — ✅ [구현완료]
분류 로직뿐 아니라 **일반 은행/카드 파일의 열 파싱**도 완료했습니다(`client/src/lib/parseExcel.ts`).
- **헤더 자동 매핑**: 열 이름 별칭 사전(`FIELD_ALIASES`)으로 `이용일/승인일시/거래일시`→날짜,
  `이용가맹점/적요/사용처`→내용, `이용금액/승인금액`→금액, `입금/출금` 분리 컬럼 등을 자동 인식.
- **제목행 자동 건너뛰기**, 정확일치 우선 매핑, 지출은 음수로 정규화, 다양한 날짜표기 처리.
- 뱅크샐러드 파일은 기존대로, 그 외 파일은 `일반(자동매핑)`으로 처리. CSV도 허용.
- 인식된 결과는 그대로 **키워드 자동분류(R1)** 로 흘러갑니다.

## R2. 서버 DB는 꼭 내가 준비해야 하나? 비용은? — [설계 판단 가이드]

### 핵심 답
현재 앱은 서버(tRPC)+DB에 데이터를 저장하는 구조라, 앱으로 내려면 **인터넷에 항상 떠 있는
DB가 필요**합니다. 다만 선택지가 있습니다.

| 방식 | 데이터 위치 | 서버 DB | 비용 | 적합성 |
|---|---|---|---|---|
| **A. 현행 클라우드 DB** | 서버 | 필요 | 월 0~1만원 | 다기기 동기화·가족 공유엔 필수 |
| **B. 로컬 온디바이스** | 폰 안(SQLite) | 불필요 | 0원 | 1인·1기기, 동기화 불필요할 때 |
| **C. 하이브리드** | 폰(원본)+서버(요약) | 소형 | 최소 | 프라이버시+동기화 절충 |

### 비용은 많이 드나? (거의 안 듭니다)
- 가계부는 **텍스트 위주 소용량**입니다. 4인 가족이 10년을 써도 수십 MB 수준.
- 무료/저가 티어로 충분: **Neon**(Postgres, 무료 0.5GB), **Supabase**(무료 500MB),
  Railway(월 $5 크레딧), PlanetScale 등. 사용자 수백 명까지 사실상 무료~월 1만원 이내.
- 지금 코드가 이미 **Postgres(Neon serverless)** 기반이라(`@neondatabase/serverless`),
  Neon 무료 티어로 바로 시작 가능.

### "정리된 값만 올리면 비용 최소화되나?" — 맞습니다 (방식 C 추천 근거)
원본 raw 파일(엑셀)을 서버에 통째로 저장할 필요는 없습니다. 지금도 **파싱된 행 데이터만**
저장하고 있어 효율적입니다. 더 줄이려면:
- **원본 엑셀 파일 자체는 저장 안 함**(이미 그럼) — 파싱 결과 행만 저장.
- **온디바이스 우선(방식 B/C)**: 파싱·분류를 폰에서 하고, 서버엔 **월별 카테고리 합계 같은
  요약치만** 올리면 프라이버시↑·용량↓. 단 "거래 상세 검색"은 폰 안에서만 됨.
- 트레이드오프: 서버에 상세를 안 두면 **다기기·가족 공유·웹 동시 조회**가 어려워집니다.
  가족 공유(락인 핵심 R4)를 하려면 방식 A/C가 필요합니다.

> 권장: **처음엔 방식 A(Neon 무료 티어)** 로 단순하게 출시 → 사용자·프라이버시 요구가
> 커지면 방식 C로 민감정보 온디바이스화. 비용 걱정은 사실상 없습니다.

## R3. 파일 업로드 없이 데이터 수집 — [외부연동]

"매번 엑셀 받아 올리기"는 이탈의 최대 원인. OS별 수집 경로:

### 결제 문자 파싱 — ✅ [파서·붙여넣기 입력 구현완료]
- **파서**(`client/src/lib/parseSms.ts`): 카드 승인/은행 입출금 문자에서 금액·날짜·시간·유형·
  가맹점·카드사를 추출(정규식 기반). 신한/삼성/현대/국민/롯데/우리/하나/농협/카카오/토스 등 인식.
- **붙여넣기 입력**(`SmsImportModal`, 대시보드 '💬 문자 입력' 버튼): 문자를 붙여넣으면 자동
  인식 → 미리보기 → 소유자/카테고리 선택 후 저장. **전 플랫폼(웹·iOS·Android)에서 동작**.

#### (후속) Android 자동 SMS 리스너 — [외부연동]
위 파서를 그대로 재사용해 **자동화**할 수 있습니다.
- `RECEIVE_SMS`/`READ_SMS` 권한 + 소형 네이티브 플러그인(BroadcastReceiver)로 승인문자 수신 →
  `parsePaymentSms()`에 원문 전달 → 자동 입력. 또는 `NotificationListenerService`로 카드사 앱 푸시 파싱.
- 구글플레이 SMS 권한 정책 심사가 까다로우니, 알림 접근 방식이 승인 가능성이 높습니다.

### iOS — 반자동 (애플이 SMS/타앱 푸시 접근을 원천 차단)
iOS는 자동 수집이 막혀 있어 **애플이 허용하는 우회로**를 씁니다.

1. **공유 시트(Share Extension)** — [설계]
   카드사 앱/문자/브라우저에서 "공유 → 우리집가계부" 하면 텍스트를 넘겨받아 파싱.
   - Capacitor에 iOS Share Extension 타깃 추가(`ios/` Xcode에서 New Target → Share Extension).
   - App Group으로 앱 본체와 데이터 공유 → 앱 실행 시 대기열의 공유 텍스트를 파싱해 입력.
2. **단축어(Shortcuts) 자동화** — [설계]
   사용자가 아이폰 "단축어 앱"에서 자동화 1회 설정:
   `○○카드에서 메시지 수신 → 메시지 본문 → (앱의 URL 스킴/App Intent)로 전달`.
   - 앱에 **App Intent**(iOS 16+) 또는 URL 스킴(`budgetapp://add?text=...`)을 노출하면
     단축어가 승인 결제문자를 앱으로 자동 전달 → 준자동 수집.
   - Capacitor에서 `CapacitorApp.addListener('appUrlOpen', ...)`로 수신 처리.

### 오픈뱅킹 / 마이데이터 스크래핑 (양 OS 공통, 가장 강력) — [외부연동]
계좌·카드 내역을 **사용자 동의하에 자동으로** 가져오는 정공법.

- **직접 마이데이터 라이선스**: 자본금·보안 요건이 커서 개인/소규모는 **사실상 불가**.
- **제휴 핀테크(스크래핑 API) 경유가 현실적 1순위**:
  - **CODEF (코드에프, 쿠콘)** — https://codef.io : 은행·카드·페이·국세청 등 계정 연결 후
    거래내역 조회. 마이데이터 라이선스 없이 시작 가능.
  - 대안: **쿠콘 API**, **팀윙크/뱅크샐러드 비즈**, 해외는 Plaid(국내 미지원).
- **월 사용료 (대략적 시장가, 2026 기준 추정치 — 실제는 영업 견적 필수)**:

  | 구간 | 대략 비용 | 비고 |
  |---|---|---|
  | 개발/테스트 | 무료~월 몇만원 | 샌드박스·소량 무료 제공 |
  | 초기 상용(소량) | **월 10만~30만원대** | 기본요금 + 호출당 과금 |
  | 성장기 | 호출 건당 수원~수십원 | MAU·조회빈도에 비례 |

  > 정확한 금액은 CODEF/쿠콘에 **직접 견적 문의**해야 합니다(공개가 아님). 초기엔 "연결계정 수 ×
  > 조회 횟수"로 과금되는 경우가 많아, **하루 1회 배치 동기화**로 호출을 줄이면 비용이 절감됩니다.

- 구현 방향: 서버에 CODEF 토큰/커넥트 흐름 추가 → 사용자별 계정 연결 → 정기 배치로 거래 수집
  → 기존 `insertTransactions` + 자동분류(R1) 파이프라인 재사용.

#### CODEF 연동 — 구체적 연결 지점 (외부 계약 필요, 코드 미포함)
> ⚠️ CODEF는 **계약·API 키·계정 연결 인증**이 있어야 실제 동작하므로 이 저장소엔 넣지 않았습니다.
> 아래 지점에 붙이면 됩니다(사업자 등록 + CODEF 가입 후):
```
1) 서버 env 추가:  CODEF_CLIENT_ID / CODEF_CLIENT_SECRET / CODEF_PUBLIC_KEY
2) server/에 codef.ts:  OAuth 토큰 발급 → /v1/kr/card/... , /v1/kr/bank/... 거래내역 조회
3) 라우터에 connectAccount(사용자 금융사 로그인 위임)·syncNow 추가
4) 수집 결과를 이 앱의 ParsedRow 형태로 매핑:
     { txDate, content: 가맹점, amount(지출 음수), paymentMethod: 카드/은행명, dedupHash }
   → insertTransactions(userId=dataUserId) 그대로 호출 → 자동분류(R1) 자동 적용
5) 정기 동기화: 하루 1회 배치(cron)로 syncNow 호출(호출당 과금 절감)
```
- **핵심**: 수집 소스만 다를 뿐, **저장·분류·집계는 지금 파이프라인을 100% 재사용**합니다.
  즉 CODEF/SMS/파일 업로드가 모두 같은 `insertTransactions → 키워드 자동분류` 흐름으로 합류합니다.

### 그 외 편의 수집 — [설계]
- **영수증 OCR 촬영**(카메라+OCR), **이메일 명세서 파싱**, **홈 위젯 빠른입력**(현금 지출).

> 추천 순서: **① Android SMS 자동 → ② iOS 공유시트/단축어 → ③ 여력되면 CODEF 오픈뱅킹**으로
> 양 OS 통합. 이 3단계면 "업로드 없는 가계부"가 됩니다.

## R4. 무료·광고 모델의 락인(Lock-in) 킬러 기능

무료+광고는 **MAU·재방문**이 전부. "매일·매주 여는 이유"를 만드는 기능들.

### R4-1. 카테고리별 예산 목표 + 50/80/90/100% 알림 — ✅ [구현완료]

**구현 내용**
- **DB**: `budgets`(카테고리별 월 목표) + `budget_alerts`(같은 달·카테고리·임계치 1회만 알림) 테이블
  자동 생성. `server/db.ts`의 `getBudgetStatus/setBudget/deleteBudget/detectNewBudgetAlerts`.
- **서버 API**: `getBudgets`(이번 달 지출·달성률), `setBudget`, `deleteBudget`,
  `checkBudgetAlerts`(새로 넘긴 임계치만 반환+기록).
- **화면**: 상단 **"예산" 탭**(`components/tabs/BudgetTab.tsx`) — 카테고리별 목표 설정 + 진행률 바
  (50/80/90/100%에서 색상 변화: 초록→노랑→주황→빨강).
- **알림**: 앱 진입·업로드 후 자동으로 임계치 확인 → **웹은 토스트**, **네이티브 앱은 로컬 알림**
  (`@capacitor/local-notifications`, `lib/budgetNotify.ts`). 문구 예: "'외식&배달' 예산의 80% 사용
  (16만/20만원)", 초과 시 "'외식&배달' 예산 초과 ⚠️".

> 참고: 현재는 **앱이 켜져 있을 때(진입·업로드 시점)** 확인하는 방식입니다. 앱을 꺼둔 상태에서도
> 밀어주는 **서버 푸시(FCM)**는 별도 인프라(Firebase 프로젝트 + 기기 토큰 관리)가 필요해 후속
> 작업으로 둡니다. 아래는 그 FCM 확장 설계입니다.

#### (후속) FCM 서버 푸시 확장 설계
요청하신 핵심 기능. 구현 설계:
```
새 테이블 budgets(userId, category, month, targetAmount)
거래 입력/업로드 시:
  해당 월·카테고리 누적 지출 계산 → 목표 대비 비율 산출
  50/80/90/100% 임계치를 "이번 달 처음 넘는 순간" FCM 푸시 1회
  (중복 방지: budget_alerts(userId,category,month,threshold) 발송기록)
문구 예)
  80%: "이번 달 '외식&배달' 예산의 80%(16만/20만원)를 썼어요 🍔"
  100%:"'외식&배달' 예산 초과! 남은 8일 조심하세요 ⚠️"
```
푸시는 **FCM(Firebase Cloud Messaging, 무료)** 로 iOS·Android 공통. 서버가 임계치 돌파를
감지해 발송.

### R4-2. 정기결제·구독 감지 — ✅ [구현완료]

**구현 내용**: '구독' 탭에서 거래 내역을 분석해 **같은 가맹점·유사 금액이 월 간격(25~35일)으로
3회 이상 반복**되면 정기결제로 자동 판정합니다. 월 고정지출 합계, 항목별 주기·다음 결제 예정일을
보여주고 **3일 이내 결제 예정은 강조**합니다. 별도 테이블 없이 `server/db.ts`의 `getSubscriptions`가
즉시 계산(읽기 전용)하고, `components/tabs/SubscriptionTab.tsx`가 표시합니다.

> (후속) "결제 3일 전 푸시"는 R4-1의 FCM 인프라가 붙으면 nextDue 기준으로 예약 발송하면 됩니다.
> 아래는 확장(별도 테이블로 상태 저장)이 필요할 때의 원래 설계입니다.

#### (후속) 상태 저장형 확장 설계 (사용자 질문)
"어떻게 구현?" → **주기성 패턴 탐지**로 구현합니다.
```
구독 후보 탐지 로직(서버 배치, 월 1회 또는 업로드 직후):
  거래를 (정규화된 가맹점명, 금액) 으로 그룹핑
  같은 그룹이 최근 N개월 동안 "월 간격 ±3일 & 유사 금액(±5%)"으로 반복되면 → 구독으로 판정
  SQL 스케치:
    SELECT content, ROUND(amount) amt, COUNT(*) cnt,
           ARRAY_AGG(txDate ORDER BY txDate) dates
    FROM transactions WHERE userId=? AND amount<0
    GROUP BY content, ROUND(amount)
    HAVING COUNT(*) >= 3        -- 3개월 이상 반복
  → dates의 간격이 대체로 28~31일이면 구독으로 확정
새 테이블 subscriptions(userId, merchant, amount, cycleDays, lastChargedAt, nextDueAt, active)
알림:
  - 결제 예정 3일 전: "넷플릭스 17,000원이 3일 뒤 결제돼요"
  - 신규 구독 감지: "새 정기결제로 보이는 항목 발견: ○○ 9,900원/월"
  - 미사용 의심: 최근 결제는 있으나 앱 카테고리상 오래 안 쓴 구독 → "정리 추천"
```
구독비 키워드(R1의 `구독비` 그룹)와 결합하면 정확도↑. **"돈 아껴주는 앱"** 이미지로 신뢰·락인.

### R4-3. 계좌(카드/은행) 표시·숨김 — ✅ [구현완료]
'계좌' 탭에서 결제수단(카드/은행/페이)별로 **표시/숨김**을 토글합니다. 숨기면 대시보드·통계·내역·
예산·구독 등 **모든 화면의 집계에서 즉시 제외**됩니다("비상금 통장·개인 카드를 가계부에서 빼기").
- `hidden_accounts` 테이블 + 9개 집계 쿼리에 제외 필터 일괄 적용(`server/db.ts`).
- `getAccounts`/`setAccountHidden`, `components/tabs/AccountsTab.tsx`.

> (후속) 가족 공유에서 "나만 보기(private)"처럼 **뷰어별** 노출 제어가 필요하면, hidden(모두 제외)과
> 별개로 `account_visibility(userId, paymentMethod, 'private')` + 조회자 기준 필터를 추가하면 됩니다.

### R4-3b. 가족 공유 가계부 — ✅ [구현완료]
'가족' 탭에서 **그룹 생성 → 초대 코드 공유 → 코드로 참여**하면, 가족이 **같은 가계부(거래·예산·규칙·
계좌)를 함께** 봅니다.
- **구현 방식(dataUserId 인디렉션)**: 그룹 멤버의 모든 데이터 접근이 **그룹 소유자의 userId**로
  라우팅됩니다. `server/_core/trpc.ts`가 요청마다 `getDataUserId`로 해석해 `ctx.dataUserId`를 주입하고,
  라우터의 모든 데이터 조회/저장(58곳)이 이를 사용합니다(신원 기준인 로그인·그룹관리만 실제 userId).
- `groups`/`group_members` 테이블, `createGroup/joinGroup/leaveGroup/getGroupInfo`,
  `components/tabs/FamilyTab.tsx`.
- 참여하면 공유 데이터셋을 보고, 나가면 본인 개인 데이터로 복귀합니다.

### R4-4. 그 외 락인 기능 — [설계]
- **주간/월간 리포트 푸시**(일요일 저녁 요약) — 정기 재방문 왕도.
- **부부/가족 공유 가계부** — 이미 사람별 분류(서준·재이·동현·혜진) 보유 → 네트워크 효과로 이탈↓.
- **예산 챌린지·무지출 데이 + 배지**(게임화) — 리텐션 최강 패턴.
- **순자산 추이 그래프**(이미 계산 로직 보유) — "돈이 늘고 있다" 성취감.
- **연말정산/소비 인사이트 카드**("작년보다 배달비 32%↑").

### R4-5. 광고 수익화 — [외부연동]

## R5. 보안 — 개인 자산 데이터 최선의 방안 — [설계·필수]

금융 데이터라 보안은 신뢰이자 심사 요건. **OS 기본 보안기능 최대 활용.**

### R5-1. OS 제공 기능 (반드시 적용)
| 항목 | iOS | Android | 용도 |
|---|---|---|---|
| **생체 잠금** ✅구현완료 | Face ID/Touch ID | BiometricPrompt | 진입·복귀 시 잠금(헤더 토글로 on/off) |
| **보안 저장소** | Keychain(Secure Enclave) | Keystore + EncryptedSharedPreferences | 토큰·비번은 여기만, 평문 저장 금지 |
| **화면 캡처/미리보기 차단** | 앱 전환기 블러 | `FLAG_SECURE` | 계좌 화면 스샷·최근앱 노출 차단 |
| **무결성/탈옥 탐지** | App Attest | Play Integrity | 변조기기·위조앱 차단 |

Capacitor 플러그인: `@aparajita/capacitor-biometric-auth`, `capacitor-secure-storage-plugin`,
`@capacitor-community/privacy-screen`(FLAG_SECURE/블러).

### R5-2. 통신·서버 보안 (현재 코드 개선점)
- **전 구간 HTTPS(TLS)** 강제 + iOS ATS/Android `cleartextTrafficPermitted=false`.
- **`DEV_AUTO_LOGIN=false`** 프로덕션 필수(현재 dev면 무조건 로그인 — 치명적).
- 세션 쿠키 `httpOnly+secure+sameSite`(코드 존재) → 프로덕션 `secure:true` 확인.
- 인증 강화: 카카오/dev 외 **토큰(JWT) 기반 + 만료·갱신**, 서버측 권한 체크.
- **저장 데이터 암호화**: DB 저장 시 암호화(클라우드 DB 기본 제공) + 계좌번호 등 민감필드는
  애플리케이션 레벨 추가 암호화 고려. 온디바이스(R2-C)는 SQLCipher로 로컬 DB 암호화.

### R5-3. 정책·규정 (스토어 필수)
- **개인정보처리방침** 게시(양 스토어 필수): 수집 항목·보관기간·삭제절차 명시.
- **데이터 최소수집 + 회원탈퇴 시 완전삭제** 기능(국내법/GDPR 대응).
- 애플 "앱 개인정보 라벨" / 구글 "데이터 보안 양식"에 재무정보 수집·암호화·삭제가능을 사실대로.

> 보안 우선순위 3: ① 앱 실행 생체잠금 ② 토큰은 Keychain/Keystore만 ③ 화면보호(FLAG_SECURE/블러).
